## კონტექსტი

ჩანაწერი (`ProductRecording`) დღეს მხოლოდ ტექნიკურ ველებს ინახავს: ხანგრძლივობას, sample rate-ს, bit depth-ს და არხებს. `Title` ფაილის სახელიდან იწყობა, `Description` კი იმპორტისას არ ივსება. კატეგორია, keywords, ხმამაღლობა და დარტყმის დრო საერთოდ არ არსებობს.

ეს სამ რამეს ზღუდავს:

1. **ძებნა და შეთავაზება.** Studio-ს „ხმა აქ“ (SRW-47b, [`phase-2b-spotting.md`](../studio-real-workspace/phase-2b-spotting.md)) მხოლოდ იმდენად კარგია, რამდენადაც კარგია მეტამონაცემები. სათაურები ტიპის `Escalator_Loop_01` „ესკალატორს“ იპოვის, მაგრამ „მექანიკურ ზუზუნს“ ვეღარ.
2. **sync point.** Studio დარტყმის დროს ყოველ ჩატვირთვაზე თავად ითვლის (SRW-47a). კატალოგში შენახული მნიშვნელობა ამას ერთხელ და ხელით შემოწმებადად აკეთებს.
3. **ხმამაღლობა.** მყიდველი ვერ ხედავს, რამდენად ხმამაღალია ჩანაწერი, მიქსამდე.

Studio-ს ფაზა 2-ის დოკუმენტმა მეტამონაცემები, UCS, ანალიზი და ძიება **ცალკე ნაკადად** გამოყო: backend, კატალოგი და ჩამოტვირთვები. ეს გეგმა ის ნაკადია.

**შესწორება 26 ოქტომბრის შეთავაზებაში:** იქ ეს იდეა Tag Manager-ზე იყო მიბმული. ნამდვილი იმპორტი `tools/recording-import/import-recordings.mjs`-ია. Tag Manager აქ ადამიანის დაწერილი ველების რედაქტორის როლს ასრულებს.

## მიდგომა

### ტექნიკური გადაწყვეტილება

ანალიზი ემატება `prepare` ნაბიჯს, რომელიც ისედაც ffprobe-სა და ffmpeg-ს იყენებს. ყველა ახალი მნიშვნელობა `manifest.json`-ში იწერება. ადამიანი მას `upload`-მდე ამოწმებს, `recordings.sql` კი მას ბაზაში გადაიტანს. იმპორტი რჩება ხელახლა გასაშვები: მეორე გაშვება არაფერს ცვლის.

ოთხი ეტაპი, რთულის გარეშე დაწყებით:

**A. სქემა და API.** Migration `018_ProductRecording_Analysis.sql` ამატებს ველებს:

| ველი | ტიპი | შინაარსი |
| --- | --- | --- |
| `Category` | `NVARCHAR(32) NULL` | UCS CatID, მაგ. `DOORWood` |
| `Keywords` | `NVARCHAR(400) NULL` | მძიმით გამოყოფილი |
| `LoudnessLufs` | `DECIMAL(5,2) NULL` | integrated, BS.1770; 400 ms-ზე მოკლე ჩანაწერზე `NULL` |
| `TruePeakDbtp` | `DECIMAL(5,2) NULL` | true peak |
| `SyncPointMs` | `INT NULL` | პირველი დარტყმა; დარტყმის გარეშე `0` |
| `AnalysisVersion` | `INT NULL` | ალგორითმის ვერსია, ხელახალი გაშვების გადასაწყვეტად |

`ProductRecordingResponse` ამ ველებს აბრუნებს. `StorageKey` და `SourceKey` ისევ არ ბრუნდება.

**B. ავტომატური ანალიზი `prepare`-ში.**
- ხმამაღლობა: `ffmpeg -af ebur128=peak=true`, integrated და true peak.
- sync point: ffmpeg ფაილს 48 kHz მონო float PCM-ად შიფრავს, ხოლო Node ითვლის spectral flux-ს და პოულობს პირველ დარტყმას პირველ 2 წამში. ალგორითმი და პარამეტრები store-ის `hits.ts`-ს ემთხვევა (SRW-46a). ორივე მხარე ერთი და იგივე სატესტო ვექტორებით მოწმდება.
- ახალი დამოკიდებულება არ ემატება.

**C. ადამიანის დაწერილი ველები.**
- იმპორტი WAV-ის ტეგებს კითხულობს (`ffprobe -show_entries format_tags`): კატეგორიას, keywords-ს, აღწერას. მათ Tag Manager-ით წერენ.
- ტეგის არარსებობისას იმპორტი ცდილობს ფაილის სახელის UCS კონვენციის წაკითხვას (`CatID_FXName_CreatorID_SourceID`).
- CatID მოწმდება UCS-ის ოფიციალური სიით. სიის ვერსია repo-ში ფიქსირდება, უცნობი CatID კი `prepare`-ს აჩერებს.
- `Description`-ის ველი უკვე არსებობს და ამ ეტაპზე პირველად ივსება.

**D. AI შეთავაზებები (არჩევითი).**
- ცალკე Python ინსტრუმენტი `tools/recording-analysis/`: `laion/larger_clap_general` (წონები Apache-2.0) zero-shot რეჟიმში UCS-ის კატეგორიების აღწერებზე.
- შედეგი manifest-ში იწერება `suggestedCategory` და `suggestedScore` ველებად. ის **არასოდეს** ხდება `Category` ავტომატურად: ადამიანი ადასტურებს.
- იმავე ნაბიჯზე embedding-ები ფაილად ინახება მომავალი სემანტიკური ძიებისთვის. ბაზაში ჩაწერა ამ გეგმაში არ შედის.
- CLAP-ის სასწავლო მონაცემები შერეული ლიცენზიებისაა. გამოყენება შიდა შეთავაზებისთვისაა და არა მომხმარებლისთვის გამოქვეყნებული შედეგისთვის. საბოლოო ნებართვა მომხმარებლისაა.

**E. Store-ში მიბმა.** კატალოგის ახალი ველები გადადის `WorkspaceSource.meta`-ში (`app/lib/arrangement/collection.ts`). დაცული `studio.$productId.tsx`-ის ცვლილება, თუ საჭირო გახდება, root-ის ცალკე ნაბიჯია.

### ალტერნატივები

- **ანალიზი ბრაუზერში, ყოველ ჩატვირთვაზე.** SRW-47a ამას ისედაც აკეთებს sync point-ისთვის. კატეგორიას და ხმამაღლობას კი კატალოგში ძებნისთვის სერვერზე ყოფნა სჭირდება.
- **ცალკე ანალიზის სერვისი (Python API).** უარყოფილია: ახალი ინფრასტრუქტურაა, იმპორტი კი ისედაც offline და ხელითაა.
- **სტემების ავტომატური გამოყოფა (Demucs).** არ შედის: ჩანაწერები stems არ არის, მუსიკის stems კი პროდიუსერისგან მოდის. ავტომატური გამოყოფის ხარისხი premium კოლექციისთვის ცალკე შესამოწმებელია.
- **ავტომატური BPM.** არ შედის **D-29z30**-ის მიხედვით.

## რაუნდები

ამ ნაკადს backend, SQL Server, ffmpeg და ადგილობრივი R2 სჭირდება. ღრუბლის ლუპი მხოლოდ store-ის dev სერვერს უშვებს და შეამოწმებდა მხოლოდ BLOCKED-ით. ამიტომ რაუნდები PC-ზე ეშვება, იგივე B → A → C წესით, ცალკე ლუპის საქაღალდეში (`tmp/catalog-loop/`) ან ინტერაქტიულ სესიებში. ამის არჩევა მომხმარებლისაა.

| რაუნდი | შინაარსი | მიღება (C) |
| --- | --- | --- |
| **K-1** spike | Tag Manager-ით დაწერილი ტეგი WAV-ის რომელ chunk-ში ხვდება და კითხულობს თუ არა მას ffprobe; `ebur128` 10 ნამდვილ ჩანაწერზე, მათ შორის < 400 ms-იანზე; sync point-ის პირველი ვერსია 10 ჩანაწერზე | ანგარიში ფაქტებით: chunk, ffprobe-ის გამოსავალი, LUFS ცხრილი, sync point-ები ხელით მონიშნულთან შედარებით. კოდი production-ში არ შედის |
| **K-2** სქემა და API | ეტაპი A | migration ორჯერ, rollback-იან ტრანზაქციაში, scratch ბაზაზე; `dotnet build` 0 შეცდომა; ტესტები: ველები ბრუნდება, `StorageKey` არ ბრუნდება, სხვისი პროდუქტი 403/404 |

| **K-4** ტეგები და UCS | ეტაპი C | Tag Manager-ით დაწერილი კატეგორია, keywords და აღწერა ბაზაში აღწევს; UCS სახელის ფაილი ტეგის გარეშე სწორად იკითხება; უცნობი CatID `prepare`-ს მკაფიო შეტყობინებით აჩერებს |
| **K-5** store-ში მიბმა | ეტაპი E | შეძენილი კოლექციის წყაროებს `meta` აქვს; SRW-47b-ის ძებნა ნამდვილ კატალოგზე პოულობს ხმას კატეგორიით; მეტამონაცემების გარეშე ძველი ქცევა უცვლელია |
