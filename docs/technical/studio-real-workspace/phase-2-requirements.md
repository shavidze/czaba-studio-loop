# Studio ფაზა 2 — დავალებები B-სთვის

Oct 20, 2026 · @Saba Shavidze

ხუთი ახალი დავალება (SRW-40…44) ერთ ჩანაწერად ჯდება backlog-ის `post_current_stage_queue`-ში, T12-GAIN-VOLUME-ის შემდეგ. ამ რიგს B უკვე იყენებს სამუშაოსთვის „მიმდინარე ეტაპის შემდეგ“. თანმიმდევრობა: ფაზა 1 → T12 (შენი 7 ოქტომბრის მოთხოვნა) → ფაზა 2, მხოლოდ შენი დასტურით. `items` და არსებული ჩანაწერები არ იცვლება.

## როგორ ემატება

დაემატება ორი ფაილი და ერთი ცვლილება backlog-ში, მიმდინარე რაუნდის დასრულების შემდეგ. ლუპი არ ჩერდება.

1. **მოთხოვნების ფაილი:** `docs/technical/studio-real-workspace/phase-2-requirements.md` — ეს დოკი markdown-ად. B მას მასალად კითხულობს, არა ინსტრუქციად (ლუპის პოლიტიკის მე-4 წესი).
2. **რიგის ჩანაწერი:** `backlog.json` → `post_current_stage_queue`-ის ბოლოს ერთი ობიექტი `PHASE2-VIDEO-SCORING`, `status: queued_after_t12_awaiting_user_go`. შიგნით ხუთი დავალებაა და `next_action_for_B` ინსტრუქცია, T12-ის ჩანაწერის მსგავსად. ჩაწერამდე ფაილის ასლი ინახება; ჩაწერა ხდება მხოლოდ მაშინ, როცა B არ მუშაობს.
3. **მოკლე შენიშვნა B-სთვის:** `root-pre-push-review.md`-ის ბოლოს ერთი აბზაცი. ამ ფაილს B უკვე კითხულობს `policy.local.md`-ის მიხედვით.

**ID-ები:** SRW-40-დან SRW-45-მდე. ახლანდელი ბოლო ID არის SRW-24, ამიტომ 25–39 ცარიელი რჩება, რომ B-ს ახალ ქვე-ელემენტებს არ დაეჯახოს. ჩაწერამდე `backlog.json`-ში დავრწმუნდები, რომ ეს ID-ები თავისუფალია. ფორმატი `SRW-NN` ძველივეა, რადგან კონტექსტის builder მიმდინარე ელემენტს `SRW-\d+` შაბლონით პოულობს.

**Root-ის ნაბიჯი ფაზა 2-ის დაწყებისას:** A-ს პოლიტიკა პაკეტების დაყენებას კრძალავს, SRW-40-ს და SRW-42-ს კი Mediabunny სჭირდება. ამიტომ ფაზა 2-ის დასტურის შემდეგ root ცალკე კომიტით აკეთებს `npm i mediabunny`-ს store-ში, აფიქსირებს ვერსიას და ამოწმებს `npm run verify`-ს. ფაზა 1-ის განმავლობაში store-ის დამოკიდებულებები არ იცვლება. სხვა ახალი დამოკიდებულება არ არის: LUFS-ისა და scene-cut-ის კოდს A თავად წერს MIT-ნიმუშების მიხედვით, ავტორის მითითებით.

## SRW-40 — ექსპორტი ვიდეოთი (MP4)

**მიზანი:** მომხმარებელი დოკში ჩატვირთულ ვიდეოს აექსპორტებს ერთ MP4 ფაილად, რომელშიც CZABA-ს მიქსია. ვიდეო ხელახლა არ ენკოდდება, მისი პაკეტები უცვლელად კოპირდება. ამიტომ ხარისხი არ იკარგება და ექსპორტი სწრაფია.

**ეტაპები** (თითო ეტაპი ერთი რაუნდია):

1. **40a — შესაძლებლობის შემოწმება და დიალოგი.** Export დიალოგს ემატება ვარიანტი „ვიდეო + მიქსი (MP4)“. ჩართულია მხოლოდ მაშინ, როცა ვიდეო-ტრეკზე კლიპი დევს.
   - ვიდეოს კონტეინერი და კოდეკი Mediabunny-ით მოწმდება (`Input` + `ALL_FORMATS`).
   - ბრაუზერის აუდიო-ენკოდერი `AudioEncoder.isConfigSupported`-ით მოწმდება: ჯერ AAC 48 kHz stereo, ვერ თუ შეძლო — Opus.
   - ვიდეო-ტრეკის მდგომარეობა მოწმდება: სწრაფი გზა მხოლოდ მაშინ მუშაობს, როცა ტრეკზე **ერთი კლიპია**, `sourceOffset = 0` და სრული სიგრძისაა.
   - თუ რამე არ გამოდის, ვარიანტი გათიშულია და მიზეზი ქართულად ეწერება. ამ ეტაპზე ექსპორტი ჯერ არ ხდება.
2. **40b — remux.**
   - მიქსი არსებული offline რენდერით კეთდება, იგივეთი, რაც WAV-ს აძლევს, ვიდეო-კლიპის დიაპაზონზე: `[clip.start, clip.start + duration]`. საჭიროების შემთხვევაში `graph.client.ts` `AudioBuffer`-ს WAV-ად კოდირების გარეშე აბრუნებს.
   - აუდიო `AudioBufferSource`-ით ენკოდდება (AAC 192 kbps).
   - ვიდეოს პაკეტები `EncodedPacketSink` → `EncodedVideoPacketSource` გზით კოპირდება.
   - გამოსავალი ფაილი `Mp4OutputFormat`-ია.
   - პროგრესი და გაუქმება `AbortSignal`-ით.
3. **40c — სინქრონის სიზუსტე.** AAC ენკოდერი დასაწყისში დაყოვნებას (priming) ამატებს და ეს პლატფორმაზეა დამოკიდებული. ამიტომ დაყოვნება იზომება ცნობილი სიგნალის ორმხრივი გავლით და cross-correlation-ით, OpenReel-ის `audio-priming.ts`-ის მიხედვით, და კომპენსირდება. მიზანი: მიქსის პირველი sample ვიდეოს პირველ კადრს ემთხვევა.
4. **40d — შეცდომები და საზღვრები.** მეხსიერება და ფაილის ზომის ლიმიტი (იგივე, რაც დოკის `too-large`-ს), Firefox-ისა და Safari-ის ქცევა, ტექსტები, რეგრესიები.
5. **40e — რამდენიმე ან შეჭრილი ვიდეო-კლიპი (არჩევითი, B წყვეტს).** ვიდეო ხელახლა ენკოდდება: კადრები `VideoSampleSink`-ით იკითხება, `VideoSampleSource`-ით იწერება, ცარიელ ადგილებში შავი კადრებია. ეს ნელი გზაა. დიალოგი წინასწარ ამბობს, რომ ხარისხი და დრო იცვლება.

**შემოთავაზებული წესები** (ID-ს B ანიჭებს):

- გამოსავალი ფაილი ვიდეო-კლიპის დიაპაზონს მოიცავს. SRW-20-ის მონაკვეთის ექსპორტი ვიდეოზე არ ვრცელდება, რადგან keyframe-ის გარეშე ჭრა ხელახალ ენკოდს მოითხოვს. დიალოგი ამას ხსნის.
- 40e-მდე რამდენიმე ან შეჭრილი ვიდეო-კლიპის შემთხვევაში ვარიანტი გათიშულია, მიზეზის ახსნით.
- ვიდეოს ორიგინალი აუდიო ფაილში მხოლოდ მაშინ ხვდება, თუ მომხმარებელს ის ლეინად აქვს მიქსში.
- ffmpeg.wasm რჩება მხოლოდ MP3-ისთვის; ვიდეოს გზაში არ გამოიყენება.

**სავარაუდო ფაილები:** `app/components/arrangement/ArrangementExportDialog.tsx`; ახალი `app/lib/arrangement/export-video.ts` (სუფთა ლოგიკა, ტესტებით) და `export-video.client.ts` (Mediabunny); `app/contexts/ArrangementContext.tsx`; `app/lib/arrangement/graph.client.ts`; ტესტები `app/lib/arrangement/__tests__/`-ში.

## SRW-41 — ხმამაღლობა (LUFS) და სამიზნე ექსპორტი

**მიზანი:** ექსპორტისას მომხმარებელი ხედავს მიქსის ხმამაღლობას. ერთი არჩევანით ფაილს პლატფორმის სტანდარტზე აყვანს: -14 LUFS YouTube-ისა და სტრიმინგისთვის, -23 LUFS ტელევიზიისთვის (EBU R128).

**ეტაპები:**

1. **41a — გაზომვის მოდული** (სუფთა TypeScript, UI-ს გარეშე), ITU-R BS.1770-4-ის მიხედვით:
   - K-weighting ორი ბიკვადრატული ფილტრით. კოეფიციენტები ნებისმიერი sample rate-ისთვის ითვლება და 48 kHz-ზე მყარად არ წერია;
   - 400 ms ბლოკები 75%-იანი გადაფარვით;
   - აბსოლუტური gate -70 LUFS, ფარდობითი gate -10 LU;
   - short-term მაქსიმუმი 3 წამის ფანჯრით;
   - true peak 4×-ზე გადიდებული sample rate-ით.
2. **41b — export დიალოგი.** რენდერის შემდეგ დიალოგი აჩვენებს სამ რიცხვს: Integrated LUFS, Short-term max, True peak (dBTP).
   - არჩევანი „ხმამაღლობის სამიზნე“: *არა* (ნაგულისხმევი), -14, -16, -23 LUFS; ჭერი -1 dBTP.

## SRW-44 — მუსიკის ავტომატური დაწევა დიალოგზე (ducking)

**მიზანი:** როცა ვიდეოში ლაპარაკობენ, არჩეული მუსიკის ლეინები თავისით იწევს, ხოლო პაუზაში ბრუნდება. მომხმარებელს ხელით ხმის მრუდი აღარ სჭირდება.

**საწყისი წერტილი:** Studio ვიდეოს საკუთარ აუდიოს უკვე შიფრავს (`decodeVideoAudio` → `buffersRef`) და ვიდეო-ტრეკი მას უკრავს. ეს არის ducking-ის ნაგულისხმევი წყარო. წყაროდ ნებისმიერი სხვა ლეინიც შეიძლება აირჩეს (მაგ. ცალკე ჩაწერილი დიალოგი).

**ეტაპები:**

1. **44a — ლაპარაკის მონაკვეთების ანალიზი** (worker, offline, დეტერმინისტული).
   - წყაროს აუდიო გადის band-pass ფილტრს (300–3400 Hz).
   - RMS 20 ms ფანჯრებით.
   - ზღვარი წყაროს საკუთარი დონიდან ითვლება.
   - ლაპარაკის დასრულების შემდეგ 300 ms ითვლება ლაპარაკად (hangover), რომ მოკლე პაუზებში მუსიკა არ ახტეს.
   - შედეგი (მონაკვეთების სია) წყაროს მიხედვით ქეშირდება.
2. **44b — მოდელი და UI.** ლეინის დეტალების პანელში ემატება „Duck under: \[ლეინი\]“. პარამეტრები:
   - სიღრმე: ნაგულისხმევი -10 dB, დიაპაზონი 0…-24;
   - attack: 50 ms;
   - release: 400 ms.

   დაწეულ კლიპებზე gain-ის მრუდი ნახევრად გამჭვირვალედ ჩანს. პარამეტრები პროექტში და history-ში ინახება.
3. **44c — ერთნაირი დაკვრა და ექსპორტი.**
   - ერთი სუფთა ფუნქცია მონაკვეთებიდან და პარამეტრებიდან gain-ის მრუდს აგებს.
   - მრუდი ცალკე duck `GainNode`-ზე იგეგმება (`setValueCurveAtTime`): რეალურ დროშიც და `OfflineAudioContext`-ის რენდერშიც.
   - loop-ის iteration-ები იმავე წესით იგეგმება, როგორც კლიპები და მეტრონომი.

**შემოთავაზებული წესები:**

- Ducking ლეინის პარამეტრია და history-ში შედის. თავად წყაროს ლეინი არ იწევს.
- მეტრონომზე ducking არ მოქმედებს.
- გამორთული ducking ექსპორტს ბაიტ-ბაიტ ისე ტოვებს, როგორც ადრე იყო.
- B ამოწმებს, ხომ არ ეწინააღმდეგება ეს არსებულ გადაწყვეტილებებს ავტომატიზაციაზე (FB-06-ის შენიშვნა: „pan envelope არ არის“). ducking ავტომატიზაციის ლეინი არ არის, ის ცალკე პარამეტრია.

**სავარაუდო ფაილები:**

- ახალი `app/lib/arrangement/ducking.ts` (ანალიზი და მრუდი, სუფთა ლოგიკა) და მისი ტესტი;
