## Finding

### C-R207-01 — Low, existed before this round: `button { cursor:pointer }` overrides the cursor utilities on `<button>`s
- **Steps:** open `/studio-lab` at 1440×900 and load the video. Click Expand (`arrangement-video-expand`). Read `getComputedStyle([data-testid=arrangement-video-drag]).cursor`.
- **Expected:** `grab`. The handle's class contains `cursor-grab`, and the CUR-VIDEO-207 clause says "still `grab`".
- **Actual:** `pointer` at 1440 and 1280.
- **Cause, proven in the browser** (`out/handle-cause.json`): the unlayered top-level rule `button { cursor: pointer; }` in `app/styles/app.css` (stylesheet rule index 100; source line 476) beats the layered Tailwind utility. Deleting only that rule through CSSOM changes the handle to `grab` at both viewports.
- **The same class of problem** (`out/cursor-audit-1440.json`, a DOM audit of every element whose base `cursor-*` utility differs from its computed cursor): disabled buttons that have `disabled:cursor-not-allowed` show `pointer`. Examples: `arrangement-zoom-range`, `arrangement-zoom-back`, `arrangement-metronome-toggle`, "Delete — the selected clip", and 7 more unlabelled ones. No other mismatch was found.
- **Not a regression:** the diff does not touch the handle line (l.971) or `app.css`. B's own baseline probe skips `pointer`, so it could never have recorded the handle as `grab`. The clause rested on an unmeasured premise.
- **B ruling needed:** either accept `pointer` on `<button>` controls and fix the task wording, or grant a layered or `!` fix of `app/styles/app.css` (a protected file) in a later round. Under the 2026-10-23 gate this Low does not block, so it goes to `deferred_low_polish` unless B bundles it.
